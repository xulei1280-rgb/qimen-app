# 紫微斗数排盘内核专项评估

> 评估日期：2026-08-13
> 阶段：只评估排盘内核；未开发页面，未改动奇门、八字、六爻。
> 结论含义：这里只验证候选是否稳定地符合本项目声明的排盘口径，不证明紫微斗数具有科学预测效力，也不把任一实现当成唯一正统。

## 1. 结论

**采用 `iztro 2.5.8` 作为后续紫微模块的排盘内核基线，固定版本和文件哈希后本地保存，不使用运行时 CDN。**

它是唯一通过全部硬门槛并达到评分线的候选，得分 **92/100**。30 个固定盘中，所选口径下没有无法解释的核心字段差异；相同输入重复两次的冻结快照哈希全部一致。`fortel-ziweidoushu 1.3.4` 继续保留为中州派独立对照，不作为运行时依赖；`@ziweijs/core 0.3.0` 因确定的日期格式缺陷、规则默认值矛盾和运限接口不足而不采用。

这不是立即集成授权。下一阶段应先写紫微模块实施计划，再以本地固定文件封装 `buildNatal(input)`、`getHoroscope(snapshot, targetDate)` 和 `getRuleMeta()`。现有三个模块以及四模块导航在本次评估中均保持不动。

## 2. 本项目固定口径

以下均为**项目选择**，不是“唯一正确”的门派结论：

| 项目 | 本次评估口径 | 映射 |
| --- | --- | --- |
| 默认时间 | `Asia/Shanghai` 北京标准时间 | 输入默认不做经度修正 |
| 真太阳时 | 可选；经度差加时间方程修正 | 修正后跨时辰必须提示并确认；修正由项目适配层完成 |
| 出生分年 | 农历正月初一 | `yearDivide: normal` |
| 运限分年 | 农历正月初一 | `horoscopeDivide: normal` |
| 虚岁 | 目标农历年减出生农历年再加一，不按生日切换 | `ageDivide: normal` |
| 闰月 | 初一至十五按前月，十六至月末按后月 | `fixLeap: true` |
| 子时 | 早子 `timeIndex=0`，晚子 `timeIndex=12` | 晚子采用 `dayDivide: forward`，逻辑日顺推一天 |
| 安星体系 | `iztro` 默认体系 | 以其“全书”默认表为准，不混入中州派四化/亮度表 |

真太阳时修正使用 `经度差分钟 = (经度 - 120) × 4`，再加常用近似时间方程：`B = 2π × (年内日序 - 81) / 364`，`EoT = 9.87sin(2B) - 7.53cos(B) - 1.5sin(B)`。这只是项目输入适配口径；`iztro 2.5.8` 本身不接收经度，也不负责弹出确认。

对照方法不是把 `iztro` 自己当成权威答案：先按冻结项目口径生成 `iztro` 快照，再将繁简体、`事业/官禄`、`交友/仆役`等名称归一，与独立的中州派实现 `fortel` 核对共同规则。最后重复运行 `iztro` 并比较整个预期对象的 SHA-256。结果为：

- 30/30 盘重复执行哈希完全一致；
- 命宫、身宫、五行局、十二宫、关键辅星和大限区间 30/30 一致；
- 十四主星除晚子逻辑日口径影响的 3 盘外，其余共同口径全部一致；

- 0 个所选候选的已确认核心实现缺陷。

这些结论是两个开源实现的工程交叉验证，不是专家定盘。若后续专家确认盘与冻结 fixture 冲突，应先分类并更新规则决策，不能静默改预期来迎合引擎。

## 5. 差异分类

| 分类 | 观察 | 数量 | 处理 |
| --- | --- | ---: | --- |
| 流派差异 | 生年四化中，`iztro default` 与 `fortel` 中州派表不同，例如庚干科星分别为太阴与天府；目标流年四化在相应天干也会不同 | 13 个本命字段、4 个流年字段 | 固定 `iztro default`；AI 和 UI 必须显示规则元数据，不混表 |
| 时间口径差异 | 两者都有早/晚子对象，但 `iztro dayDivide: forward` 将晚子推进逻辑日；`fortel` 保持本日农历日，因此 3 个样本的主星位置不同 | 3 个主星字段 | 本项目选择 `forward`；晚子输入明确标记，真太阳时跨入晚子必须确认 |
| 实现缺陷 | `@ziweijs/core 0.3.0` 的 `Date` 格式化使用 `getDay()`，实测 `2000-08-16` 输出 `2000-08-03`；早子时范围常量为 `23:00~12:59`；文档称真太阳时默认开启，代码却只在显式真值时开启 | 3 项 | 候选淘汰，不修补后采用 |
| 暂时无法解释 | 所选 30 盘核心字段中没有 | 0 | 若未来出现，立即阻止采用/发布 |

`@ziweijs` 日期缺陷虽然暂未改变其内部农历换算结果，但会污染冻结快照的输入回显和审计证据，所以仍属于硬门槛失败，不能降级为“显示小问题”。它的 `getHoroscope(index)` 只返回某一大限内年龄/年份映射，没有本项目需要的 `targetDate → 大限＋流年宫位＋流年四化`完整语义。

## 7. 后续实施边界

下一阶段实施计划必须遵守：

1. 将固定哈希的 `iztro.min.js` 保存到项目本地；不从 CDN、远端 API 或第三方排盘服务运行时加载。
2. 用单一适配层导出：
   - `buildNatal(input)`：完成时间口径确认后，生成深冻结的本命盘快照；
   - `getHoroscope(snapshot, targetDate)`：只能从冻结快照派生大限和流年；
   - `getRuleMeta()`：返回引擎版本、源码/文件哈希及本报告第 2 节全部口径。
3. 真太阳时修正跨时辰时先显示标准时与修正时，取得确认后才调用 `buildNatal`。
4. AI 只读取冻结快照和 `getRuleMeta()`；不得自行安星、改宫位、补算四化，或在一次回答里混用中州派与默认表。
5. 后续页面范围仍为本命＋大限＋流年、结构化说明＋AI 解读、四模块统一导航。统一导航只改导航结构和样式；奇门、八字、六爻的计算、历史记录、AI 上下文和存储键保持原样，并重跑现有全部校验。

本报告未增加运行时依赖，未复制任何候选库到正式项目，也没有实现紫微页面。
